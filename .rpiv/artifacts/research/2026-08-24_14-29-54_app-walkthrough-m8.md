# Research: M8 workflow app-walkthrough — el agente usa la app como usuario y documenta su funcionalidad

## Research Question

Skill pack `frida-app-walkthrough` en `src/tools/` con el molde exacto de frida-tea (index/resolver/skills/workflow), registrando el patrón builtin `app-walkthrough` sobre frida-extensible-workflows: exploración secuencial con frida-agent-browser sobre sesión pre-autenticada del usuario, análisis paralelo con subagents sobre artefactos en disco, entregables en `docs/funcional/` (markdown multi-archivo + dashboard HTML autónomo), resolver 3-capas reutilizado, 0 deps npm nuevas, tests vitest en `test/frida-app-walkthrough/`. (Cadena de discover: `.rpiv/artifacts/discover/2026-08-24_13-40-47_app-walkthrough.md`.)

## Summary

El molde skill-pack de frida-tea/frida-aidd replica completo (fábrica + registro + resolver 3-capas + tests) sin tocar el motor. El hallazgo estructural central: **el supuesto del FRD "la sesión persistente de D34 sobrevive entre stages" es verdadero para el proceso del navegador pero falso para su accesibilidad** — el nombre implícito de `ManagedSession` es un hash aleatorio por instancia (`session.ts:74`) y las hijas del workflow no cargan `agent_browser` (`pi-session.ts:747-748` registra "main only"; `frida-agent-execution.ts:79-107` carga solo 4 provider hooks) ni `ask_user_question` (`pi-session.ts:703`, solo sesión principal). El checkpoint del motor es booleano puro (`index.ts:322`, `:677`) — no transporta "30 pantallas vs todo". Decisión del desarrollador (checkpoint): el script navega vía `shell()` con `--session <nombre>` explícito (`hasExplicitSession`, `session.ts:25` lo soporta hoy) y el presupuesto se pregunta con `ask_user_question` en sesión principal ANTES del lanzamiento, entrando por args pre-resueltos. La señal `snapshot -i` (body a11y + tabla de refs + origin + screenshot) ES suficiente para documentar propósito/rol/inventario offline; las validaciones requieren capturas post-error deliberadas del explorador. El dashboard HTML no puede usar el panel Remote React (WebNode ≠ documento); la técnica probada es heredoc determinista del script (`writeText`, `ship.ts:134-142`). El presupuesto `maxScreens` vive en lógica del script (el motor no tiene dimensión "pantallas", `core/budget.ts`); `maxMinutes` puede traducirse a `durationMs` como backstop. Tres precedentes de packs (aidd, tea, motor) muestran los puntos débiles sistémicos: gates de artefacto, mkdir -p, y salida LLM sucia — planearlos desde el día 1.

## Detailed Findings

### Sesión pre-autenticada D34 y ciclo de vida en el workflow

- El navegador vive en un **proceso externo al tool**, keyed por nombre `--session`: cada tool call es un spawn nuevo y nadie cierra el navegador entre stages — persistencia estructural entre procesos. El único cierre es best-effort al `session_shutdown` de la sesión que instancia la extensión.
- El nombre implícito es `frida-<hash(cwd|Date.now()|random)>` por instancia (`session.ts:74`); la instancia vive en el closure de la extensión de la sesión principal (`ensureSession`, `src/tools/frida-agent-browser/index.ts:91`). Cualquier segunda instancia deriva un nombre distinto y lanzaría navegador nuevo, no el autenticado.
- **Las hijas del workflow no tienen `agent_browser`**: `pi-session.ts:747-748` ("Sesión main only (las hijas de workflow quedan curadas: providers + gates)"); `createWorkflowChildFactories` (`frida-agent-execution.ts:79`) devuelve exactamente 4 factories (softtek-provider, z-ai-provider, frida-enterprise-provider, frida-provider-audit). La exclusión es por omisión de factory, no denylist (`WORKFLOW_EXCLUDED_TOOLS` en `frida-agent-execution.ts:117` no lista `agent_browser`).
- El sandbox del script solo expone `{agent, shell, withWorktree, prompt, checkpoint, parallel, pipeline, phase, log, args, Promise, JSON, Math}`; `Date/eval/Function/process/require/console/...` son `undefined` (`core/execution.ts:322`) — el script no puede tocar el navegador directo, solo vía `shell()`.
- **Seam resuelto (checkpoint desarrollador)**: `shell("agent-browser --session <nombre> snapshot -i --json > docs/funcional/...")` — `validateShellCommand` no tiene denylist, `executeShellCommand` spawnea con `shell: true` (redirección a disco incluida, crucial porque el sandbox no tiene fs). El pin explícito `--session` hace que `prefixFor` omita el prefijo automático (`session.ts:99-100`).
- **El guard de refs obsoletas queda irrelevante bajo navegación vía shell()**: el estado `refSnapshot/refsStale` vive por instancia (`session.ts:125`) y solo se puebla/invalida con resultados tool-mediados; la navegación externa es invisible. La protección se sustituye por disciplina del script: snapshot → actuar `@ref` → re-snapshot tras cada navegación (misma receta que `prompt.ts:29` enseña). Extender factories de hijas multiplicaría caches divergentes del guard, no resolvería.
- Reanudación tras interrupción: el journal JSONL es resumible, pero una run atascada en `running/awaiting` de sesión muerta es "orphan stuck" irrecuperable (solo `workflow_gc`); la historia real del FRD (artefactos parciales válidos + juez CONCERNS) = corrida nueva que lee los artefactos del disco. El navegador sigue vivo bajo el nombre pinneado.

### Señal `snapshot -i` para documentación offline

- Cadena verificada: receta `open → snapshot -i → click/fill @eN → snapshot -i` (`prompt.ts:29`) → `renderSnapshot` (`src/tools/frida-agent-browser/results/snapshot.ts:45`) = body a11y con `[ref=eN]` inline + tabla `renderRefList` (`snapshot.ts:25`, `- @eN role "name"`, ordenada por `compareRefIds` `snapshot.ts:13`).
- **Suficiencia**: body + tabla de refs + origin/title + screenshot SÍ alcanzan para propósito/rol/inventario offline. Dos huecos: (1) la tabla de refs es plana — pierde jerarquía (solo vive en el body); (2) `highValueControlRefIds` existe solo como texto de guideline, sin campo estructurado.
- **Validaciones NO existen en snapshot estático**: constraints de formulario y mensajes de error solo aparecen como evidencia de comportamiento — el explorador debe llenar mal → submit no-destructivo → capturar snapshot post-error (el FRD ya lo exige como req 3).
- `nextActions` es prescindible offline: solo se emiten tras navegación exitosa o fallos, no en snapshot exitoso.
- Persistencia de capturas: vía tool existe `outputPath` (`src/tools/frida-agent-browser/schema.ts:137`) → `applyOutputPath` (`src/tools/frida-agent-browser/run.ts:230`) → `details.savedFile` (`src/tools/frida-agent-browser/index.ts:454`) que vuelca el envelope completo; vía `shell()` la redirección stdout aterriza el mismo envelope crudo.
- Registro por pantalla única (dedup + `maxScreens` verificable ex-post): origin canónico + title (llave de dedup; `pushstate` distingue vistas SPA pero no tabs internos de la app — secundario: conteo de refs), timestamp/orden, path del snapshot, paths de screenshots + `artifactVerification`, lista de refs, acciones ejercidas + resultados, nombre de sesión + índice vs `maxScreens` (el juez cuenta origins únicos en el log).

### Pregunta de presupuesto (bootstrap)

- `checkpoint()` devuelve solo `"approved"/"rejected"` de punta a punta: el RPC exige boolean del bridge, `workflow_respond` exige `approved: boolean` (`src/tools/frida-extensible-workflows/index.ts:677`), el journal persiste boolean. El `context` del checkpoint (≤4096 bytes) es salida display-only. No existe pregunta de forma libre con retorno dentro del sandbox.
- `ask_user_question` es el único canal estructurado con opciones clicables y vive SOLO en sesión principal (`pi-session.ts:703`); las hijas son headless (`bindExtensions({ mode: "print" })`).
- `BudgetApprovalRequest` existe en el core (`src/tools/frida-extensible-workflows/core/types.ts:186`) y `workflow_respond` lo menciona, pero el host Frida nunca lo cablea — cero usos.
- **Decisión del desarrollador (checkpoint)**: el agente principal pregunta con `ask_user_question` ANTES de invocar `workflow` (opciones "30 pantallas/15 min", "todo", números), y lanza `workflow({ name: "app-walkthrough", args: { url, maxScreens } })` con args pre-resueltos. Tras el lanzamiento, corrida desatendida. "Todo" = centinela `maxScreens: 0` (o ausencia de tope).
- El prompt del bootstrap se resuelve en launch-time congelado en el script estático — la respuesta del usuario nunca puede entrar a la corrida en curso; el único canal de datos libre son los args del lanzamiento. Patrón molde: `review: "manual"|"auto"` de tea (arg pre-resuelta + checkpoint opcional post-hoc).
- Consecuencia de prompts: el preámbulo "haz exactamente UNA pregunta de presupuesto si los args no traen tope" vive en el prompt de la skill para sesión principal; los agentes de stage siguen headless al estilo `MURAT_PREAMBLE`.

### Fanout de análisis paralelo

- `parallel()` tipificado (`ParallelTasks → ParallelResult`) corre `Promise.all` puro — **sin tope de concurrencia** en el puerto Frida (el `concurrency` del schema no se lee). Semántica de fallo todo-o-nada por grupo: el primer error se re-lanza; no hay resultados parciales.
- Cada tarea pasa por `withStructuredOutput(createFridaAgentSpawner(ctx))`: sin schema es passthrough; con schema appendea "OUTPUT FORMAT (strict)…", parsea laxo, repara con errores concretos (máx. 2 intentos totales, `src/tools/frida-extensible-workflows/structured-output.ts:290`), y ante hijo sin texto adjunta `nullDiagnostic` (`frida-agent-execution.ts:145`) al repair prompt.
- Molde de fanout claveado: `generateTeaAutomateWorkflow` — bootstrap determinista con outputSchema → corte en script `list = list.slice(0, maxTargets)` (`src/tools/frida-tea/workflow.ts:427`) → `parallel("targets", tasks)` (`:444`) → agregado JS puro (`green = list.filter(...)`) → gate detached contra disco. El espejo `parallel("files"` de test-review en `:510`.
- **`maxScreens` no existe como dimensión del motor**: `validateBudget` solo acepta tokens/costUsd/durationMs/agentLaunches (`src/tools/frida-extensible-workflows/core/budget.ts:6`; unión `BudgetDimension` `core/types.ts:146`). El tope de pantallas vive en lógica del script (dedupe por origin + slice); `maxMinutes → durationMs` es traducción posible como backstop, pero en el bridge Frida `usage.durationMs` acumula duraciones de hijos (no wall-clock) y el chequeo ocurre antes de cada spawn.
- Contrato de artefactos: "los agentes ESCRIBEN a disco con sus file tools y devuelven resumen/JSON — el filesystem es la cadena de custodia" (header `frida-tea/workflow.ts:1-15`). Gates `shell("test -s …")` tras cada claim (precedente #83).

### Política de acciones (submits no-destructivos)

- El piso Tier-A es **soft** (prompt, no código): `prompt.ts:29` veta TODO submit ("Stop before order/post/purchase/submit"). El FRD lo relaja para búsquedas/filtros — el "endurecimiento" del pack es respecto a navegar sin preamble.
- **El veto debe vivir como constante-preamble separada** (estilo `MURAT_PREAMBLE` `src/tools/frida-tea/skills.ts:41`, interpolada por el ctx-helper FUERA del mapa de stages): el resolver reemplaza prompts completos sin fusión de secciones — un override de equipo del stage `explore` que omita el veto pasaría en silencio. Un preamble no-stage no es direccionable por `.frida/*/stages.json`.
- `--allowed-domains` sobre sesión pre-autenticada viva está **bloqueado por diseño** (flag launch-scoped + sesión implícita activa → `failureCategory: "policy-blocked"`, `src/tools/frida-agent-browser/index.ts:352`): exigiría fresh y perdería el login. El FRD ya lo atenúa a "cuando aplique". Con pin explícito + shell(), el flag no aplica vía wrapper.
- **Gap de auditoría**: `approvals.jsonl` (frida-permission-system) registra decisiones de gate pero NO captura el argv de `agent_browser` (solo extrae `path`/`command` del input; el schema del tool no los tiene). La evidencia real del argv vive en `details.args`/`details.session` del tool result (`src/tools/frida-agent-browser/index.ts:503`, transcript) y en el journal del motor si el stage declara `outputSchema` con manifiesto de acciones — esa es la vía auditable para el criterio "sin submits destructivos". `provider-audit.log` de las hijas solo registra tráfico LLM.
- `guardRefMutation` cubre click/fill/select/... (`MUTATION_COMMANDS` `src/tools/frida-agent-browser/ref-guard.ts:21`) pero `submit` literal NO está en el set (`:39` NAVIGATE_COMMANDS aparte); no opina sobre destructividad — la invariant "sin irreversibles" descansa 100% en prompts. Bajo shell() el guard no corre en absoluto; la disciplina snapshot→actuar→re-snapshot es la sustitución.

### Entregables `docs/funcional/` + dashboard HTML + catálogo

- `docs/funcional/` no existe aún (cero coincidencias en el repo). Precedencia de artefactos análoga a `TEA_ARTIFACTS_DIR` (`skills.ts:38`).
- **El panel `WorkflowPanel.tsx` NO sirve para el HTML autónomo**: es Remote React donde el host serializa WebNode para el webview de Frida — no produce documento HTML; ninguna exportación a HTML plano existe.
- Técnica probada (aidd): `writeText` heredoc con fence-guard (`src/tools/frida-aidd/ship.ts:134-142`) + serialización determinista (`stSerialize`/`stWrite`, `src/tools/frida-aidd/workflow.ts:143`/`:167` — "UN único writer idempotente: el orquestador determinista; los agentes LLM jamás escriben este archivo"). Reparto híbrido espejo aidd: los 4 md de contenido = agentes de síntesis con JSON agregado inyectado (patrón tea-test-review); `README.md` (índice) + `index.html` = script determinista desde el MISMO inventario serializado (una fuente de verdad → markdown y HTML nunca divergen; diff-stable para `app-rewalk`).
- IDs estables por entidad (P01/J01/R01/A01) y screenshots nombrados por ID (`screenshots/P01-login.png`), nunca por timestamp — mecanismo central de diff-comparabilidad. Header de metadatos de corrida con orden fijo y marker de procedencia.
- Catálogo `/help`: `HELP_TOOLS` (`src/extension.ts:3906`, forma `{match, file, howTo, label}`; entrada frida-tea con label en `:4048`). `openHelpDoc` abre `path.join(context.extensionPath, relPath)` — **los archivos `docs/tools/frida-app-walkthrough.md` + `docs/how-to-frida-app-walkthrough.md` DEBEN existir** o el preview rompe: catálogo + docs es un commit atómico. Faltante default aterriza en `howTo ?? file`; miss abre README y lista labels (`:4173`). Falta además: fila en el README del repo (patrón `README.md:211`) y cross-link del how-to.

### Ejecución end-to-end one-shot

- Launch: `workflow({name})` → `findBuiltinPattern(name).resolve(args, {cwd})` (`src/tools/frida-extensible-workflows/index.ts:289-291`, verificado) → script estático + snapshot inmutable → `runWorkflowInStore` foreground o background.
- **Checkpoint requiere background**: en foreground el bridge lanza error (requiere UI del webview). El follow-up del checkpoint re-dispara el turno del agente principal (`index.ts:322`: "Responde con workflow_respond({ runId, name, approved: <true|false> })").
- Background: AbortController + registro, follow-up de resultado/error re-dispara turno (one-shot desatendido se sostiene aquí); clasificación `/CANCEL/` → stopped, `/BUDGET/` → budget_exhausted.
- Resiliencia: repair in-place de outputSchema (2 intentos) → si no alcanza, fallo del grupo = fallo del run (sin resultados parciales) → `workflow_retry` (replay del journal, solo la fallida corre) / `workflow_resume` (solo budget_exhausted, requiere patch de presupuesto). Sin auto-retry.
- Si nadie responde un checkpoint: run queda `awaiting` para siempre (sin timeout).

## Architecture Insights

- **Launch-time congela todo**: `resolve()` valida args + resuelve 3 capas + genera script estático (identidad de journaling estable). Ningún dato del usuario puede entrar a una corrida en curso — solo args de un lanzamiento nuevo. Esto dicta el flujo: preguntar antes, lanzar después.
- **Dos mundos de sesión**: la sesión principal tiene tools ricos (`agent_browser` con guard/bash-guard/gates, `ask_user_question`); las hijas del workflow son headless con solo provider hooks. El patrón pack exitoso (tea/aidd) delega a hijas SOLO lectura/análisis/escritura de archivos, y mantiene la interacción en la principal.
- **El filesystem es la cadena de custodia**: agentes escriben artefactos con sus file tools y devuelven JSON corto (outputSchema); gates `test -s` verifican claims; el journal persiste valores de retorno. El fanout de análisis lee disco, nunca navegación viva.
- **Writer determinista vs writer agéntico**: archivos de estructura/índice con requerimiento de diff-stability los escribe el script (heredoc, `stWrite`); contenido narrativo lo escriben agentes desde JSON agregado inyectado.
- **Override de prompts = reemplazo total**: la personalización 3-capas no fusiona secciones; cualquier invariant de seguridad en prompts debe vivir en constante-preamble no direccionable por las capas.
- **El motor no sabe de "pantallas"**: presupuestos del dominio (pantallas únicas) se enforce en lógica del script con agregados deterministas verificables ex-post contra los artefactos.
- **Patrón de registro de packs**: import + entrada `{name, factory}` en `pi-session.ts:631`; la dirección de dependencia es consumidor → motor (el factory solo registra; nada del ciclo de vida).
